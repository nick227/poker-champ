# Lesson System Design

This document describes the lesson system architecture, identifies complex and error-prone areas (based on real issues we’ve seen), and proposes concrete ways to simplify and harden it.

---

## 1. Root cause: three contracts too loosely aligned

The lesson system effectively has **three contracts** that are not tightly aligned:

| Contract | What it defines | Where it lives |
|----------|-----------------|----------------|
| **Content / snapshot** | Shape of step-config and snapshot JSON (projected or hand-authored). | Content files, `projectSpecToSnapshots`, export scripts. |
| **Client table / action-bar** | What the table and action bar need to render and enable actions (e.g. full `hero.actionOptions` including wager bounds). | `buildTableSceneModel`, `getActionContext`, action bar permissions. |
| **Submit / grading** | What the server accepts and how it grades (action type, optional amount). | `LessonGradingEngine`, `normalizeLessonAction`, `validateActionAnswer`. |

**The unclickable / incomplete button bug is exactly what happens when these drift.** Content produces under-specified snapshots; the client compensates with repair logic; multiple pipelines produce inconsistent shapes. The fix is not mainly in the button layer—it is to make **DB snapshots canonical** at import/storage time so the client consumes one stable contract.

**Blunt summary:** The system is failing because content is under-specified, the client is compensating, and multiple pipelines create inconsistent snapshot shapes. The fix is to normalize ACTION_STEP snapshots at import/storage time and have the client consume one stable contract.

---

## 2. Overview and goals

The lesson system lets users:

- Run through **steps** (info, multiple-choice, or table-action).
- See a **table snapshot** per step (optional for INFO/MCQ).
- **Submit answers** (option key for MCQ; action + optional amount for ACTION_STEP).
- Get **feedback** (correct/incorrect, follow-up text, EV/takeaway when configured).

Lessons are authored as **content files** (step-config + snapshots), then **synced into the DB** via scripts. The **client** loads lessons and attempts from the **API** and drives the table UI and submission flow.

## 3. Current architecture (high level)

```
┌─────────────────────────────────────────────────────────────────────────────┐
│  CONTENT (source of truth)                                                   │
│  content/lessons/content/<lessonId>/step-config.json, snapshots/*.json       │
└───────────────────────────────────┬─────────────────────────────────────────┘
                                    │ seed / import scripts
                                    ▼
┌─────────────────────────────────────────────────────────────────────────────┐
│  DB (Prisma)                                                                 │
│  Lesson, LessonStep (snapshotJson, gradingSpecJson, options), LessonAttempt  │
└───────────────────────────────────┬─────────────────────────────────────────┘
                                    │ GET /api/lessons/:id, POST .../attempts, .../submit
                                    ▼
┌─────────────────────────────────────────────────────────────────────────────┐
│  CLIENT                                                                      │
│  useLessonSession → LessonContent → ActiveTableView + ActionBar / MCQ panel │
│  submitAction → toLessonActionPayload → submitStep(lessonId, attemptId,     │
│                 stepId, answer)                                              │
└───────────────────────────────────┬─────────────────────────────────────────┘
                                    │ answer: { type, amountCents? } or { optionKey }
                                    ▼
┌─────────────────────────────────────────────────────────────────────────────┐
│  SERVER (submit)                                                             │
│  LessonAttemptService.submitStep → validate → normalizeGradingSpec →        │
│  gradeStep → actionKeyFromAnswer → persist + update attempt                  │
└─────────────────────────────────────────────────────────────────────────────┘
```

- **Step types:** `INFO_STEP`, `MCQ_STEP`, `ACTION_STEP`.
- **ACTION_STEP:** Uses a table snapshot; hero must act. Answer is an action (`fold` | `check` | `call` | `bet` | `raise` | `all_in`) plus optional `amountCents`.
- **V2 runtime:** Some ACTION_STEPs use a “migrated” path (`isV2ConfiguredStep`) with decision-node runtime and extra submit logic; the rest use the classic submit-only path.

## 4. Data flow in detail

### 4.1 Content → DB

- **Step config:** `content/lessons/content/<lessonId>/step-config.json` defines steps (id, sequence, type, snapshotPath, gradingSpecJson, options for MCQ).
- **Snapshots:** Either hand-authored JSON files under `./snapshots/` or generated by **projectSpecToSnapshots** from a minimal hand spec (produces `TableSnapshotPayload` per hero decision).
- **Projected snapshots** (from `projectSpecToSnapshots`) set `hero.actionOptions` via **actionOptionsForExpected(expectedAction)** — only capability flags and `primaryWagerAction`; **no** `minRaiseTo` / `maxRaiseTo`.
- **Seed script** (`scripts/seed-lessons-content.ts`) reads config + snapshot files, validates (e.g. ghost lessons: hero seat, toActSeat, actionOptions match expected action), and upserts into `Lesson` / `LessonStep` (including `snapshotJson`).

So the **single source of truth** for what the user sees is the **DB**. Content is the input to the pipeline that writes the DB.

### 4.2 API → Client

- **getLesson(lessonId):** Returns lesson with steps. Each step includes `snapshot: step.snapshotJson`, `options`, and grading/display fields derived from `gradingSpecJson`.
- **startOrResumeAttempt(lessonId):** Returns attempt (id, status, currentStepIndex, submittedSteps). Current step index is computed from submitted steps.
- **submitStep(lessonId, attemptId, stepId, answer):** Validates answer for step type, grades, persists attempt step, returns feedback.

### 4.3 Client: snapshot → table UI and actions

- **LessonContent** gets `step` and `stepSnapshot = step?.snapshot` from session.
- **Scene model:** `buildTableSceneModel(stepSnapshot, …)`:
  - Builds seat context, `isMyTurn` (hand.toActSeat === hero.seat), pot, cards, etc.
  - Takes `snapshot.hero.actionOptions` and runs:
    - **mergeCallWithStack** (derive call when possible from stack/round bet).
    - **fillWagerBoundsFromSnapshot** (derive `minRaiseTo` / `maxRaiseTo` when missing so BET/RAISE are clickable).
  - **getActionContext(isMyTurn, actionOptions, connectionStatus)** → `showActions`, `allowedActions`, `wager`.
- **Action bar** uses `getActionBarPermissions(actionContext)`; buttons are enabled only when the corresponding permission is true. **WAGER** is true only when `actionContext.wager` is set, which requires wager bounds.
- For non–ACTION_STEP steps, the client uses **buildReplayDisabledSceneModel** so the bar shows a message instead of live actions. **tableMode** and **hideBottomSection** control whether the bottom block is shown at all (lessons now use `tableMode="live"` so the bottom is always visible).

### 4.4 Client: click → submit

- **Action bar** calls `onAction({ type: "FOLD"|"CHECK"|"CALL"|"BET"|"RAISE"|"ALL_IN", amount? })`.
- **LessonContent.handleAction** can enrich payload (e.g. ALL_IN with `amount: sceneModel.heroStackCents` when missing).
- **useLessonSession.submitAction** runs **toLessonActionPayload(payload)** → `{ type: "fold"|"check"|… , amountCents? }`, then **submitAnswerEvent(normalized)** → `lessonService.submitStep(lessonId, attemptId, stepId, answer)`.

### 4.5 Server: submit → grade

- **validateActionAnswer(stepType, answer):** For ACTION_STEP, requires **normalizeLessonAction(answer) != null**.
- **normalizeLessonAction(answer):** Reads `obj.type` and `obj.amount` or `obj.amountCents` (both supported so client can send `amountCents`).
- **gradeStep(spec, stepType, answer):** For ACTION_STEP, normalizes answer, compares submitted action to expected (with BET/RAISE/ALL_IN normalization), returns isCorrect, response, followUp, etc.
- **actionKeyFromAnswer** produces a display key (e.g. "raise", "all_in") for feedback.

## 5. Complex and error-prone aspects

These have caused or can cause bugs like the ones we’ve seen (unclickable buttons, only Raise working, no feedback after click).

### 5.1 Snapshot shape vs table/action-bar expectations (main structural bug)

- **Problem:** **Projected lesson snapshots are not full live-action snapshots.** The table layer expects a **live-style** snapshot: `hero.actionOptions` with not only flags but also **minRaiseTo/maxRaiseTo** for WAGER. Projected snapshots don’t set these, so without client-side derivation the Bet/Raise button stays disabled even when `canBet`/`canRaise` is true. The client has to “repair” with mergeCallWithStack and fillWagerBoundsFromSnapshot—so the system is already telling us that lesson snapshots are not authoritative enough for the UI consuming them. That is fragile.
- **Risk:** Any new snapshot source that omits wager bounds will behave the same unless the client keeps filling them.
- **Coupling:** Table scene model and action bar are coupled to the full `HeroActionOptions` contract; lesson content is coupled to “whatever the server stores in snapshotJson.”

### 5.2 Two pipelines for ACTION_STEP snapshots (second biggest source of weirdness)

- **Projected snapshots** (projectSpecToSnapshots): minimal spec → state machine → one snapshot per hero decision; actionOptions from **actionOptionsForExpected** (flags only, no bounds).
- **Hand-authored or export snapshots:** e.g. from replay export or manual JSON; may include full actionOptions or not.
- **Risk:** If snapshots can come from both pipelines, the client is forced to support **multiple shapes forever**. That almost always leads to: some lessons working, some partly working, some rendering weird action bars, and resume bugs that are hard to reason about.

### 5.3 Answer payload contract (client ↔ server)

- **Problem:** Client sends `{ type, amountCents }`; server originally read only `obj.amount`, so amounts were dropped and grading could still pass by type while other logic might expect an amount.
- **Risk:** Any new client or server code that assumes a single field name will reintroduce bugs. Multiple shapes (e.g. `amount` vs `amountCents`) increase cognitive load and regression risk.

### 5.4 Step identity vs snapshot identity

- **Problem:** `currentStep` is `lesson.steps[resolvedStepIndex]`; the snapshot shown is that step’s `snapshot`. If the DB has the wrong snapshot on a step (e.g. step 2 row has step 1’s snapshot), the UI shows the wrong state and actions don’t match what the server expects.
- **Danger:** Step row can be correct, gradingSpec can be correct, but the **snapshot attached to that row** can be wrong. Then everything looks “kind of right” but behavior is wrong. This is the kind of bug that wastes hours because the UI is technically behaving correctly against the wrong snapshot.
- **Risk:** Seed/import bugs or manual DB edits can desync step index and snapshot. Hard to detect without cross-checking step id vs snapshotId or expected action.

### 5.5 Table mode and bottom visibility

- **Problem:** For non–ACTION_STEP we previously used `tableMode="replay"`, which set `hideBottomSection={true}` and hid the entire action/message area. INFO/MCQ lessons (e.g. L16) showed no buttons or message.
- **Risk:** Table mode is reused for real replay; overloading it for “lesson but not action step” made behavior non-obvious and easy to break.

### 5.6 V2 vs classic ACTION_STEP path

- **Problem:** Two code paths for ACTION_STEP: classic (submit only) and “migrated” (isV2ConfiguredStep + decision runtime + optional extra submit). handleAction and submit logic branch on this.
- **Risk:** Duplication and branching; fixes must be applied in both paths; testing must cover both.

### 5.7 ALL_IN and missing amount

- **Problem:** Action bar sends `{ type: "ALL_IN" }` with no amount; lesson grading can still work by type, but feedback or analytics might expect an amount. Client now enriches ALL_IN with hero stack when available.
- **Risk:** Other action types or future features might assume amounts are always present; contract is implicit.

## 6. Proposals to flatten and harden

### Recommended first three changes

If choosing only three changes to remove most of the fragility:

1. **Normalize snapshotJson at seed/import time** — make every ACTION_STEP snapshot in the DB canonical and UI-ready (see Priority 1 below).
2. **Add strict ACTION_STEP validation during seed** — fail fast when a snapshot is inconsistent (see Priority 3 below).
3. **Standardize action answer payload to `{ type, amountCents? }`** — one official format; server can keep backward compatibility internally but all new code uses one shape (see Priority 2 below).

Those three changes give one stable runtime contract and catch problems before they become UI mysteries.

---

### Priority 1 — Make DB snapshots canonical

**For every ACTION_STEP snapshot stored in the DB, ensure:**

- `hero.actionOptions` is **complete** (all fields needed for the table/action-bar contract).
- `minRaiseTo` / `maxRaiseTo` **exist when wager is legal** (canBet/canRaise and primaryWagerAction set).
- `hand.toActSeat` **matches** `hero.seat` when the step is “hero to act.”
- The **expected action** (from gradingSpec) is **representable** by the snapshot (e.g. expected BET implies canBet and wager bounds).

**Contract in one sentence:** An ACTION_STEP snapshot stored in DB **must be sufficient, by itself, to render the correct action bar without client-side reconstruction of wagering legality.**

**Where:** In the write path—seed script and/or any import that writes `LessonStep.snapshotJson`. When writing an ACTION_STEP snapshot (whether from projected spec or hand-authored/export), run a **normalize step** that derives and persists full `hero.actionOptions` (e.g. fill wager bounds from hand/table/hero stack). The client should not need to infer core wagering legality from partial lesson data; that logic belongs in content projection / import normalization, not in the view model.

**Benefit:** One stable runtime contract. Client can assume snapshots are complete; over time, client-side repair (mergeCallWithStack, fillWagerBoundsFromSnapshot) can be reduced or removed.

---

### Priority 2 — Unify action payload

- **Pick** one canonical shape: `{ type, amountCents? }`. Document it as the only official format.
- **Client:** Always send that shape; no second field name (`amount` vs `amountCents`).
- **Server:** Can keep backward compatibility (read both `amount` and `amountCents`) internally, but all new code and docs should use `amountCents` only.
- Reduces client/server drift and regression.

---

### Priority 3 — Snapshot validation at seed time

**Add a validator that fails fast if an ACTION_STEP snapshot is inconsistent.** Seed/import should **reject** (or refuse to write) cases such as:

- `canRaise: true` (or canBet) but **missing** `minRaiseTo` / `maxRaiseTo`.
- ACTION_STEP but **hero is not to act** (hand.toActSeat !== hero.seat).
- **Expected action is wager** but snapshot cannot build wager context (e.g. no bounds, no primaryWagerAction).
- **Step sequence / id** says one thing, snapshot metadata (e.g. snapshotId, street) says another—optional cross-check if you add metadata.

**Operational invariant:** If expected action is BET/RAISE/ALL_IN, the snapshot must produce a **non-null wager/action context** under the canonical client rules (i.e. after any agreed, minimal normalization, the table/action-bar can construct a valid wager context from the snapshot alone).

That catches the problem before it becomes a UI mystery.

---

### Long-term simplification: remove client-side repair

Right now the client does:

`snapshot → mergeCallWithStack → fillWagerBoundsFromSnapshot → getActionContext`

**Goal over time:** Move to:

`snapshot → getActionContext`

Maybe one tiny normalization pass is acceptable, but not major rule reconstruction. Every time the client “repairs” the snapshot, you create the possibility that UI legality differs from grading legality, lesson runtime differs from author intent, or one component repairs differently than another. Once DB snapshots are canonical (Priority 1), client repair can be phased out.

---

### 6.1 Explicit “lesson table” mode

Using replay mode to mean “non-action lesson step” is a design smell. Introduce a distinct **lesson table mode** (e.g. `tableMode="lesson"` or `lessonTableMode`) so that:

- Lesson + ACTION_STEP → show action bar (or message when disabled).
- Lesson + INFO/MCQ → show message area, never hide bottom.

Stop using `tableMode="replay"` to mean “lesson but no actions.” Makes rendering rules easier to reason about and prevents bugs like L16.

---

### 6.2 Single submit path for ACTION_STEP

Two ACTION_STEP paths (classic vs V2) is too much. Even if internals differ, the **outer contract** should be one path:

- Normalize answer (type + amountCents).
- Submit once.
- Receive result.
- Optionally run extra runtime hooks (e.g. V2 decision node).

Not two different mental models in the UI. Unify so fixes and logging live in one path.

---

### 6.3 Document and centralize lesson action payload

- Document the exact answer shape per step type (ACTION_STEP: `{ type, amountCents? }`; MCQ: `{ optionKey }`) in this doc or a small “lesson contract” file.
- Centralize in the client: one function that builds the payload for the lesson API (e.g. toLessonActionPayload); keep that as the single place.

---

### 6.4 E2E and contract tests

- **E2E:** At least one lesson per “shape”: INFO-only, MCQ-only, ACTION_STEP-only (e.g. L54), mixed (e.g. L16). Assert: buttons visible where expected, submit leads to feedback, next step advances.
- **Contract:** A test or schema that asserts the client’s action payload matches what the server’s normalizeLessonAction and validateActionAnswer expect.
