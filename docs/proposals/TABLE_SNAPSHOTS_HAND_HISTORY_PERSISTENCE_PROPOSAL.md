# Table Snapshots + Hand History Persistence Proposal

Date: February 16, 2026
Status: Proposed
Owner: Multiplayer Reliability Track

## 1. Why This Epic Next
This is the highest-value next epic because it directly improves:
- Auditability: deterministic reconstruction of what happened at the table.
- Dispute resolution: reliable evidence for action order, pot math, and payouts.
- Recovery confidence: room restarts/rejoins can validate state against persisted truth.
- Reliability leverage: future features (admin review, player history UI, anti-cheat signals) depend on trustworthy table history.

## 2. Goals
1. Persist enough state to replay and verify every completed hand.
2. Persist periodic table snapshots to support fast state inspection and recovery debugging.
3. Guarantee action/payout history is complete and internally consistent with pot accounting.
4. Keep runtime performance stable by writing asynchronously where safe and batching where practical.

## 3. Non-Goals (for this epic)
- Full production-grade event sourcing migration.
- Public-facing hand-replayer UI.
- Advanced long-term cold storage/archive pipeline.

## 4. Current State (as of February 16, 2026)
- Snapshot contract for realtime gameplay exists and is stable (`packages/realtime-contract/src/table.ts`).
- Core hand tables exist: `Hand`, `HandPlayer`, `HandAction`, `HandPayout` (`prisma/schema.prisma`).
- `HandHistoryService` exists with methods for `startHand`, `recordAction`, `recordPayout`, `endHand` (`src/engine/persistence/HandHistoryService.ts`).
- Dealer currently ensures player rows but does not fully wire hand-history calls on every action/payout path (`src/engine/Dealer.ts`).
- Seat session persistence exists (`TableSeatSession`) and improves rejoin reliability.

## 5. Proposed Architecture

### A. Persisted Hand History as System of Record for Completed Hands
- Treat `Hand` + `HandPlayer` + `HandAction` + `HandPayout` as authoritative hand audit data.
- Enforce hand lifecycle invariants:
  - one `Hand` row per runtime handId.
  - every accepted in-hand action creates one `HandAction` row.
  - every payout creates one `HandPayout` row.
  - `Hand.endedAt` and ending stacks are always finalized.
- Authority boundary:
  - hand history tables are the system of record.
  - snapshot logs are forensic breadcrumbs for debugging and investigation only.
  - recovery authority must remain with hand rows and runtime rules, not snapshot replay.

Deterministic ordering fields:
- `HandAction.actionIndex Int` (monotonic per hand, generated by Dealer).
- `HandPayout.payoutIndex Int` (monotonic per hand, generated by Dealer).
- Recommended uniqueness constraints:
  - `@@unique([handId, actionIndex])` on `HandAction`
  - `@@unique([handId, payoutIndex])` on `HandPayout`
- Benefits:
  - stable chronology without relying on clock order.
  - simpler reconciliation and replay.
  - resilient to timestamp drift/skew.

### B. Persisted Table Snapshot Log for Fast Inspection/Recovery Evidence
Add a new append-only table for snapshot breadcrumbs:
- `TableSnapshotLog`
  - `id`
  - `tableId`
  - `handId` (nullable when waiting)
  - `snapshotId`
  - `reason` (enum)
  - `street`
  - `payloadJson` (full snapshot payload)
  - `payloadBytes`
  - `stateHash`
  - `createdAt`

`reason` enum values:
- `HAND_START`
- `ACTION_ACCEPTED`
- `STREET_TRANSITION`
- `POT_UPDATED`
- `SHOWDOWN`
- `HAND_END`
- `PLAYER_JOIN`
- `PLAYER_LEAVE`

Indexes:
- `(tableId, createdAt)`
- `(tableId, handId, createdAt)`
- unique `(snapshotId)`

Retention:
- Configurable TTL cleanup (for example 7-30 days), with optional keep-last-N per table to cap storage.

Payload guardrail:
- hard payload cap (example: `256 KB`).
- compute/store `payloadBytes` on persist attempt.
- if payload exceeds cap:
  - log warning with `tableId`, `snapshotId`, and `payloadBytes`.
  - skip persistence for that snapshot to prevent runaway growth.

### C. Write Path Rules
- Synchronous writes (must succeed before progressing hand):
  - `startHand`
  - `recordAction`
  - `recordPayout`
  - `endHand`
- Asynchronous/batched writes (best effort with retries):
  - snapshot logs (`TableSnapshotLog`) after emit.
- Failure policy:
  - If DB is enabled and critical hand-history write fails, fail fast and mark hand/table as errored to avoid silent corruption.
- Write invariants:
  - each critical write includes `tableId` and `handId`.
  - each critical write executes in one logical transaction per call.
  - `recordAction` must not mutate runtime state until persistence succeeds (`DB first, state second` for critical action transitions).

## 6. Implementation Plan

### Phase 1: Wire Complete Hand History
1. Wire `startHand` call in dealer hand-start flow.
2. Wire `recordAction` in action handler for all accepted player actions.
3. Wire `recordPayout` in both showdown and last-player win paths.
4. Wire `endHand` with board/reason/ending stacks.
5. Add structured log correlation keys: `tableId`, `handId`, `snapshotId`, `actionId`.
6. Add deterministic indices generated by Dealer:
   - `actionIndex` for each persisted action.
   - `payoutIndex` for each persisted payout.
7. Enforce transactional write behavior for each critical call with explicit `(tableId, handId)` scope.
8. Ensure runtime action mutation only commits after successful `recordAction` persistence.

Acceptance:
- Every completed hand has persisted hand header, participants, actions, payouts, and ending stacks.
- No missing action/payout rows in deterministic integration tests.

### Phase 2: Add Table Snapshot Persistence
1. Add Prisma model + migration for `TableSnapshotLog`.
2. Add persistence service/repository for snapshot writes.
3. Persist snapshot payload on every `sendTableSnapshotToAll`/`sendTableSnapshotToUser` emission point.
4. Add dedupe guard on `snapshotId`.
5. Add payload size controls:
   - store `payloadBytes`.
   - skip persistence + warn when payload exceeds hard cap.
6. Add operational throttle config: `SNAPSHOT_LOG_SAMPLE_RATE` (default `1.0`).

Acceptance:
- Snapshot logs are queryable by table and hand.
- Snapshot payload schema version and hash are stored for offline validation.

### Phase 3: Consistency Guards + Reconciliation Jobs
1. Add hand-level reconciliation checks:
  - `sum(payouts) == pot` for hand end.
  - action chronology monotonic by `createdAt`/sequence.
  - ending stacks across all `HandPlayer` rows equal starting stacks + payouts - bets.
2. Add nightly/on-demand verification script:
  - detect incomplete hands.
  - detect payout mismatch.
  - detect snapshot gaps.
3. Emit reliability metrics counters for all mismatch categories.

Acceptance:
- Reconciliation script reports zero inconsistencies on staging test runs.
- Metrics visible for failed writes and mismatches.

### Phase 4: Retention, Access, and Operational Readiness
1. Add TTL cleanup job for `TableSnapshotLog`.
2. Add admin/internal API endpoint(s) for hand + snapshot lookup by `tableId` and `handId`.
3. Document incident-response runbook for dispute investigation.

Acceptance:
- Storage growth remains bounded via retention policy.
- On-call can retrieve hand + snapshot evidence in one query flow.

## 7. Testing Plan
1. Unit tests for persistence services (`HandHistoryService` + snapshot log service).
2. Integration test: one full hand writes complete action/payout history.
3. Integration test: disconnect/reconnect hand still records correct chronology.
4. Integration test: showdown side-pot hand persists matching payouts.
5. Integration test: snapshot log count increases for major transitions.
6. Regression test: DB-disabled mode remains non-crashing/no-op (existing behavior).
7. Fuzz test: random valid action sequences over N hands, then reconciliation assertions pass.

## 8. Rollout Strategy
1. Introduce feature flag: `FEATURE_TABLE_SNAPSHOT_LOG_PERSISTENCE`.
2. Deploy Phase 1 (hand history completeness) first; validate on staging.
3. Run one-week shadow mode for hand-history writes:
   - persist and measure write errors/latency.
   - do not fail-fast yet; emit metrics only.
4. Flip fail-fast for critical hand-history writes after shadow-mode stability.
5. Enable snapshot log persistence in staging with short TTL and `SNAPSHOT_LOG_SAMPLE_RATE=1.0`.
6. Run two-browser release gate + automated harness + reconciliation script.
7. Enable in production with monitoring and fallback toggle; lower sample rate (for example `0.1`) if DB load is noticeable.

## 9. Risks and Mitigations
- Risk: write amplification and DB latency.
  - Mitigation: async snapshot writes + targeted indexes + TTL cleanup.
- Risk: partial write corruption during hand progression.
  - Mitigation: fail-fast on critical writes + reconciliation tooling.
- Risk: schema drift between runtime snapshot and stored payload.
  - Mitigation: persist `version` and `stateHash`, enforce contract validation pre-write.

## 10. Definition of Done
1. All accepted actions and payouts are durably persisted for completed hands.
2. Snapshot logs are persisted and queryable for dispute/debug workflows.
3. Reconciliation script detects no integrity mismatches on staging gate suite.
4. Manual two-browser release gate passes with persistence evidence.
5. Runbook and retention policy are documented.
6. Given a `handId`, the system can reconstruct a complete chronological action timeline from DB alone.
