# Hand Replayer Generation Analysis (`/history`)

## Scope
This document explains when and how hand replay data is generated, persisted, and surfaced from the `/history` flow.

## 1. Where `/history` comes from in client routing
- Route registration: `apps/client/src/registry/screen.registry.ts`
  - `history.path = "/history"`
  - Screen file: `apps/client/app/history.tsx`
- `/history` loads:
  - `GET /api/history/overview`
  - `GET /api/history/hands`
  - `GET /api/history/hands/:id` (on hand selection)

## 2. Replay data model (what is actually replayed)
Replay is driven by `TableSnapshotLog.payloadJson` rows (SYSTEM perspective snapshots), not by rebuilding state from hand actions.

Primary storage tables:
- `Hand`, `HandPlayer`, `HandAction`, `HandPayout` (core history)
- `TableSnapshotLog` (frame-by-frame snapshots used by replay)

Schema reference:
- `prisma/schema.prisma` models: `Hand`, `HandPlayer`, `HandAction`, `HandPayout`, `TableSnapshotLog`

## 3. Exact generation timeline (when data is written)

### A. Hand history rows (always needed for `/history`)
Generated by dealer lifecycle services:
- Hand start: `HandLifecycleService.startHand()` -> `handHistory.startHand(...)`
  - File: `src/engine/dealer/services/HandLifecycleService.ts`
- Each accepted action: `ActionService.execute(...)` -> `SettlementService.recordAcceptedAction(...)` -> `handHistory.recordAction(...)`
  - Files: `src/engine/dealer/services/ActionService.ts`, `src/engine/dealer/services/SettlementService.ts`
- Payouts: `SettlementService.recordAcceptedPayout(...)` -> `handHistory.recordPayout(...)`
  - File: `src/engine/dealer/services/SettlementService.ts`
- Hand end: `SettlementService.finalizePersistedHand(...)` -> `handHistory.endHand(...)`
  - File: `src/engine/dealer/services/SettlementService.ts`

Persistence guard:
- `PersistenceFacade` only enables DB writes when:
  - `DATABASE_URL` is set
  - `NODE_ENV !== "test"`
- File: `src/engine/persistence/PersistenceFacade.ts`

### B. Replay frame rows (`TableSnapshotLog`)
Generated from snapshot emission pipeline:
1. Dealer emits snapshots through `SnapshotService.emitToAll/emitToUser`
   - File: `src/engine/dealer/services/SnapshotService.ts`
2. `SnapshotService` invokes `emitHook` with canonical SYSTEM payload
3. `PokerRoom` provides that hook via `onTableSnapshotEmitted`
   - File: `src/rooms/PokerRoom.ts`
4. `PokerRoom` maps snapshot reason and writes with `TableSnapshotLogService.writeSnapshot(...)`
   - File: `src/rooms/PokerRoom.ts`
5. `TableSnapshotLogService` inserts into `tableSnapshotLog`
   - File: `src/engine/persistence/TableSnapshotLogService.ts`

Feature flag gate (critical):
- Snapshot persistence runs only when `FEATURE_TABLE_SNAPSHOT_LOG_PERSISTENCE=true`
- Checked in `PokerRoom` via `isTableSnapshotLogPersistenceEnabled()`
- File: `src/config/features.ts`

## 4. How `/history` decides replay availability

### A. List endpoint (`GET /api/history/hands`)
- File: `src/http/HandHistoryRouter.ts`
- For each returned hand, router checks `TableSnapshotLog` for rows where:
  - `handId IN (...)`
  - `payloadJson.hero.userId == "SYSTEM"`
- If present, `hasReplay: true`; otherwise false.

UI usage:
- `apps/client/src/components/domain/history/HandListItem.tsx`
  - Shows "Replay Hand" button only when `hasReplay === true`
  - Navigates to `/replay/[handId]`

### B. Detail endpoint (`GET /api/history/hands/:id`)
- File: `src/http/HandHistoryRouter.ts`
- Loads `snapshots` using `ReplayFrameService.getFramesForHand(handId)`
- `ReplayFrameService`:
  - Reads SYSTEM snapshot logs for that hand
  - Validates payload schema
  - Filters to replay-relevant reasons
  - Deduplicates by `snapshotSeq`
  - Returns sorted frames
- File: `src/engine/persistence/ReplayFrameService.ts`

### C. Replay screen
- File: `apps/client/app/replay/[handId].tsx`
- Hook `useHandReplayTableProvider` fetches `getHandDetail` and requires `handDetail.snapshots.length > 0`
- If snapshots are empty, replay screen shows: `No replay data for this hand.`
- File: `apps/client/src/hooks/useHandReplayTableProvider.ts`

## 5. Why replay may be missing even when hand exists
Common causes:
1. `FEATURE_TABLE_SNAPSHOT_LOG_PERSISTENCE` is not `true`
2. Hand was played before flag was enabled (historical hands won’t backfill automatically)
3. Server running with persistence disabled (`DATABASE_URL` missing or `NODE_ENV=test`)
4. Snapshot rows exist but are filtered out (non-SYSTEM payloads or non-replay reasons)
5. Snapshot payload skipped by `TableSnapshotLogService` due to:
   - sampling (`SNAPSHOT_LOG_SAMPLE_RATE`)
   - payload size cap (`SNAPSHOT_LOG_MAX_BYTES`)

## 6. End-to-end sequence summary
1. Hand starts -> `Hand` + `HandPlayer` rows written.
2. Actions/payouts occur -> `HandAction` + `HandPayout` rows written.
3. Dealer emits snapshots during hand lifecycle.
4. If snapshot persistence flag is on, SYSTEM snapshots are written to `TableSnapshotLog`.
5. `/history/hands` marks `hasReplay` based on presence of snapshot logs.
6. `/history/hands/:id` returns normalized `snapshots` array.
7. `/replay/[handId]` replays those snapshots using `TableLayout` + replay controls.

## 7. Practical verification checklist
- Confirm env:
  - `FEATURE_TABLE_SNAPSHOT_LOG_PERSISTENCE=true`
  - `DATABASE_URL` set
  - `NODE_ENV` not `test`
- Play a new hand after enabling flags.
- Check API:
  - `/api/history/hands` -> hand has `hasReplay: true`
  - `/api/history/hands/:id` -> `snapshots.length > 0`
- Open `/replay/[handId]` from history list.

## 8. Optional SQL spot-checks
```sql
-- hands visible to a user are controlled by Hand/HandPlayer/PokerPlayer joins,
-- but replay availability is driven by TableSnapshotLog presence per handId.

SELECT handId, COUNT(*) AS frames
FROM TableSnapshotLog
WHERE handId IS NOT NULL
GROUP BY handId
ORDER BY frames DESC;
```
